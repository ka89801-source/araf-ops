# أعراف — واجهة العمليات الجديدة

التصميم المرفق يعمل على **نفس مشروع Supabase الحالي** ونفس البيانات والخدمات الأصلية. لا يحتاج إنشاء قاعدة أخرى، استنساخًا، ترحيلًا، أو تشغيل SQL.

العمل محصور في `codex/araf-ops-v2-isolated-20260921`. كلمة isolated في اسم البرنش تشير إلى فصل تغييرات الكود، ولا تعني قاعدة بيانات منفصلة. لم تُغيّر البرنشات الأصلية أو إعدادات نشرها.

## الربط

- `js/supabase.js` الأصلي هو مصدر رابط Supabase والمفتاح العام، ويستخدم مشروع `yuoforvbxpwislmdrvvb` نفسه.
- تسجيل الدخول بحساب الإدارة الحالي عبر Supabase Auth والتحقق بواسطة `ops-business-session` الأصلي.
- الطلبات والقضايا: `service_requests`؛ الفريق: `employees`؛ الدعم: `support_tickets`؛ النشاط: `request_activity_log`.
- المنشآت وطلباتها واستهلاكها تُقرأ بواسطة `ops-business-snapshot` الحالي.
- إنشاء طلب التفعيل وتحديثه وتفعيل الحساب تستخدم واجهات `araf.company` الحالية، بما فيها رموز الدخول الفعلية التي يعيدها الخادم.
- الفاحص يرسل ملخصًا يراجعه المستخدم إلى مساعد `araf.online/api/free-ask` الأصلي. المفاتيح السرية تبقى في خادم المساعد الأصلي. تُعرض الإجابة ومصادرها كما يعيدها؛ لا تُختلق درجات مخاطر من إجابة نصية.
- `api/ops/[route].js` وسيط لمسارات محددة، يمرر جلسة المستخدم للتحقق الأصلي. لا يستخدم مفتاح service-role ولا يدير الجداول.
- `api/legal-check.js` يتحقق من صلاحية الإدارة قبل استدعاء المساعد، ولا يمرر رمز جلسة الإدارة إليه.

**حفظ تعديل من الواجهة الجديدة يغيّر السجل نفسه الذي تعرضه الواجهة القديمة.** هذا مقصود لأن القاعدة مشتركة. فصل البرنش يحمي نشر الكود؛ لا ينشئ عزلًا للبيانات.

## العمليات المنفذة

تحميل الطلبات على صفحات حتى اكتمال النتائج، تصنيف القضايا بأسمائها الحقيقية، الإسناد، تغيير الحالة، الإغلاق وإعادة الفتح، الملاحظات، متابعة القضية، قيمة الطلب وحالة الدفع، الطلبات الخارجية، إضافة سجل موظف، تذاكر الدعم وتحويلها بواسطة RPC الأصلي، طلب الحذف واعتماده بواسطة مستخدم آخر وRPC الأصلي، وطلب تصفير العداد وفق الآلية الأصلية. نجاح الحفظ يُعرض بعد رد الخادم؛ فشل الصلاحيات أو تعارض نسخة الطلب لا ينتج نجاحًا محليًا وهميًا.

تُحدّث القائمة كل 30 ثانية عند ظهور الصفحة وعدم وجود نافذة مفتوحة أو عملية حفظ. مصدر الأرقام والرسوم هو السجلات المحمّلة، دون عملاء أو أحداث أو رسائل محاكاة. نسبة حِمل الموظف مؤشر تقديري بمرجع 12 طلبًا؛ ليست سعة مخزنة في قاعدة البيانات. تظهر أخطاء التحميل بدل العودة لبيانات تجريبية.

## حدود قائمة تحتاج مراجعة

- واجهة المنشآت الأصلية التي أمكن فحصها توفر القراءة والتفعيل، ولا توفر عقد حفظ فعليًا لإسناد طلبات المنشآت وتغيير حالتها وحساب حصصها. هذه الأزرار معطلة بوضوح حتى يتوفر مسار الحفظ المعتمد؛ لم تُضف جداول أو إجراءات بديلة.
- المراسلات المستقلة والتذكيرات الجماعية في الملف المرفق كانت محاكاة. لا توجد خدمة أصلية موثقة لها؛ الملاحظات داخل الطلب تعمل، ولا تُعرض رسائل «تم الإرسال» الوهمية.
- إضافة موظف تضيف سجلًا للفريق وفق المنصة الأصلية؛ لا تنشئ حساب Auth ولا ترسل كلمة مرور.
- المرفقات الموجودة تُفتح بروابطها المتاحة؛ لا يوجد رفع ملفات جديد دون عقد التخزين المعتمد.
- الحسابات وصلاحيات Supabase وقيود الجداول الحالية تظل هي المرجع. لم تُعدّل سياسات RLS أو تُستخدم مفاتيح سرية لتجاوزها.

## البناء والتحقق

```sh
python araf-ops-src/build.py
python araf-ops-src/build.py --check
node --test tests/*.test.cjs
```

`index.html` ناتج من ملفات `araf-ops-src/`. لا تعدّله يدويًا.

الاختبارات المحلية تستخدم خدمات محاكاة ولا تقرأ أو تكتب بيانات الإنتاج. تغطي ترقيم الصفحات، الصلاحيات، تعارض التعديلات، حفظ الملاحظات، RPC التحويل والحذف، حدود وسيط الاتصال، الفاحص، والقوائم الفارغة والممتلئة. لم يُجر اختبار دخول أو حفظ فعلي بحساب المستخدم.

## المتبقي للتشغيل

1. أنشئ نشر معاينة من هذا البرنش على استضافة تدعم وظائف Node في `api/`، مثل Vercel، مع إبقاء نشر الإنتاج وبرنشه كما هما. `vercel.json` يحدد مدد وظائف المساعد والعمليات. لا تستخدم استضافة HTML ثابتة فقط لأن وسيط الاتصال يحتاج خادمًا.
2. افتح رابط المعاينة وسجّل الدخول بحساب الإدارة الحالي. لا توجد مفاتيح قاعدة جديدة مطلوبة.
3. تحقق من ظهور نفس أرقام الطلبات والقضايا والمنشآت والفريق. عند اختبار الحفظ استخدم تعديلًا مقصودًا فعليًا، لأن البيانات مشتركة.
4. راجع الحدود أعلاه ومسار حفظ طلبات المنشآت قبل اعتماد المنصة كاملة. اعتماد التصميم ونشره على الإنتاج خطوة لاحقة مستقلة.

لم يُنشر هذا التغيير على المنصة الحالية ولم تُنفذ اختبارات كتابة عليها.
